# M2.15C — In-scene NPC address versus player summon

**Scope:** deterministic offline decision + read-only operator preview.
**State:** Draft PR, no merge or live operation authorized.

## Why this distinction matters

The owner-local M2.15B Sentinel preview verified exactly one persisted
Discord inbound but returned `activity_unknown`. That is expected: the trusted
`readNpcSummonFacts` projection has no structured evidence for current
activity, hearing/perception or other active scenes.

The current summon policy answers a **different question** from "may an NPC
who is already present answer the person addressing them?" We must not
silently treat that summon-specific uncertainty as permanent prohibition
of conversations. But physical location alone also cannot prove speech
availability, DM permission or an NPC's awareness.

## Advisory contact policy

`src/communication/scene-contact.ts` is deliberately pure and has no
Discord/DB/LLM/provider/transport dependencies.

- **`direct_in_scene`** requires authoritative active world/NPC/scene facts,
  exact co-location, a non-revoked same-world/NPC/context local grant, current
  NPC state version and a grant issued **before** the authenticated source
  event. Even with all these facts, `activity_unknown` results in
  `needs_review`, **not** an automatic reply.
- **`summon_request`** is the only possible advisory path when no local
  presence evidence exists. It reuses `evaluatePlayerSummon`; player text
  cannot create a grant, move the NPC or retroactively turn a prior request
  into speech.
- **`unverified`** handles invalid facts, a revoked/foreign/stale grant,
  location mismatch, inactive lifecycle and other contradictory evidence.
  These cannot be downgraded into a valid summon or a new local interaction.
- Known busy activity can delay, explicit unavailability, lack of awareness
  or a competing active scene can block, and unknown activity/perception/
  other-scene evidence requires review. The pure decision makes **no claim**
  about DM authorization.

Every decision returns `canGrantPresence=false`, `canGenerate=false` and
`canSend=false`. A `candidate_needs_review` is only an advisory finding.

## Existing trusted boundary stays in charge

The merged M2.15B owner operator `--preview` still checks PostgreSQL 17
identity/role, read-only transaction, route-revision migration, the original
single authorized Discord source event, player mapping, exact app mention,
NPC target, scene, route, activation policy audit and pre-event presence,
and zero response deliveries.

Only **after** those invariants pass, it obtains structured NPC facts and
a matching evidence record from the trusted read-only DB transaction. The
new policy then contributes **additive, redacted fields**:

```json
{
  "contactPath": "direct_in_scene",
  "speechStatus": "needs_review",
  "speechReason": "activity_unknown"
}
```

These fields join the original fixed output `status`, `availability`,
`reason`, `canGenerate=false`, `canSend=false`, `readOnly=true`. The
existing M2.15B `needs_availability_review` field remains unchanged for
backward compatibility; it comes from the _summon_ evaluator. The new
`speechStatus` distinguishes direct address from summon availability.

Invalidated event/grant/route/player mapping still returns only
`integrity_blocked`. It does not reveal source text, user IDs, DM secrets,
NPC private activity, current location or internal SQL exceptions.

## Verification and acceptance

- Unit: direct versus summon, missing evidence, stale event-before-grant,
  foreign/changed world/NPC/scene identity, stale version, revoked presence,
  unknown perception/activity/conflicting scene, no unauthorized speech,
  fabricated DM claims and sensitive-data redaction.
- PostgreSQL rollback-only synthetic fixture: accepted inbound event,
  original unchanged M2.15B verdict plus direct-scene speech annotation,
  no DB mutation caused by preview; revoked local presence prevents any
  direct-scene classification or delivery.
- Full quality/security/PG17/isolated Gateway DEV CI is required on the
  **exact final PR HEAD** before requesting an owner merge decision.

The existing owner DEV `lw-dev-npc-e2e-001` event is consumed and must not
be rearmed or replayed through intake. This PR does not alter that world.

## What is still missing before first real NPC speech

- Trustworthy, provenance-bearing activity/perception/scene occupancy
  observation (existing [Issue #18](https://github.com/Strisko-SVK/living-world/issues/18)).
- Explicit DM/world-scoped decision for how ordinary direct in-scene NPC
  dialogue can proceed under narrative constraints, with independently
  audited approval or policy setting. Do not pretend that `unknown` means
  "free" or "aware".
- Revalidation inside the final **transactional action boundary**, including
  source message age, scene/role/presence changes, concurrency, and existing
  M2.9/M2.10 response/delivery fences.
- A separately owner-approved single outbound pilot and later normal runtime
  wiring. No outbound permissions can be inferred from this preview.

No migration, owner-local database mutation, live Gateway, Discord send,
paid LLM call, deployment or merge is authorized by this implementation.
