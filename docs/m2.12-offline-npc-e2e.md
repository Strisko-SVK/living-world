# M2.12 — Offline NPC end-to-end workflow (WIP)

## Scope and authority

This milestone is a **simulation harness**, not authorization to run the real response pipeline or Discord outbound transport. The coordinator in `src/offline/npc-e2e.ts` is intentionally not imported by `src/runtime.ts`, `src/index.ts`, the Gateway CLI, or the operator delivery CLI.

The coordinator only sequences injected ports; **injection alone is not a safety barrier**. Its test-only composition root is `src/offline/npc-e2e.test-fixture.ts`: it constructs the fake provider and fake transport internally, checks `NODE_ENV=test`, rejects remote/non-test database URLs and live Discord/LLM configuration, checks the actual PostgreSQL database name, and requires a synthetic `delivery-test-<UUID>` world. It is imported only by tests, not runtime or operator CLI.

## Required authoritative boundaries

- M2.8 determines intake eligibility, world/scene mapping and actor identity.
- M2.9 trusted local-presence evidence must predate the original Discord event; no later grant retroactively authorizes it.
- M2.7's context snapshot, visibility policy, response claim, provider-attempt fences and persisted response govern generation.
- M2.10's route resolution, immutable outbox, claim, preflight, ACK and uncertain/recovery rules govern delivery.
- M2.11's outbound HTTP client must not be used by this offline milestone. Fake ACKs are never evidence of Discord delivery.

The coordinator's shallow preflight and route comparison are only additional fail-closed checks, **not** replacements for those repository-level guards. The coordinator deliberately refuses to send preexisting responses on replay and never automatically retries errors.

## Findings and remaining gates

- Disabling scene policy during generation prevents response persistence (`response_blocked`).
- Disabling the original Discord route during generation can leave a persisted NPC response, but M2.10 rejects outbound delivery (`delivery_blocked`), with no fake send. The response/outbox distinction is intentional in the test contract and requires review of later route restoration/reconciliation semantics.
- The harness' local database URL, database-name and synthetic world-key gates are additional defenses, not proof of OS-level network isolation or ephemeral database provenance. A privileged actor who deliberately supplies a replacement database client could imitate those properties; do not use outside disposable CI/test environments.
- Competing orchestrators, delayed source events, route restoration after blocked delivery, uncertain ACK recovery, and full independent security/code review remain acceptance gates.
- Do not merge, deploy, connect Discord, enable real LLM, or reuse the consumed Step 14 live pilot without separate owner authorization.

## Restored-route and concurrency audit (5 November 2026)

- The original route may be disabled during fake generation. The M2.7 response is persisted, but M2.10 refuses to create a delivery while the mapping is inactive. Restoring the same route **does not** cause automatic send or coordinator replay: the interaction is already responded, and the offline coordinator returns `ineligible`.
- **Separate operator-only edge case:** after the original route is reactivated, an explicit operator `preview` for that old response can return `ready` because no outbox was ever created. This means a later explicitly authorized operator execution could send old speech. The code currently lacks a durable revocation epoch/tombstone that would permanently retire that interaction. This is recorded as an operator workflow limitation, not an automatic-delivery or NPC-presence-revocation failure.
- If the outbox existed before route revocation, M2.10 changes it to terminal `blocked`. Reactivation does not reopen that outbox, and no fake transport send occurs.
- Eight concurrent offline invocations of the same received interaction are expected to persist one response and generate one fake delivery acknowledgement; this is covered by an actual PG17 concurrency test. Existing M2.10 tests independently cover disputed ACK and explicit operator reconciliation.

**Backlog follow-up:** if operators later need route deactivation to permanently retire every previously received interaction, design a persistent revocation epoch/tombstone separately. Do not introduce a schema migration for this rare administrative edge case without an explicit need.

## Security review: historical reply authorization after route restoration

**Finding LW-M2.12-SEC-01 (P2 / deferred operator-route edge case).** A response persisted while the original Discord mapping was inactive has no outbox and cannot be sent by the offline coordinator. Once the identical mapping is reactivated, a separately authorized operator's delivery preview can become `ready`, and a new explicit delivery preparation can produce a valid outbox. This is not an automatic send, but it demonstrates that _current route validity_ alone is insufficient to prove that an earlier request still has consent to be answered.

**Possible future policy:** revocation of an entire Discord scene route could retire pre-revocation, undelivered interactions for that route. Reauthorization restores the route for _new_ interactions, not historical ones. A separate explicit DM action would be required to issue a new task or message; do not resurrect the old source event. An outbox already in terminal `blocked` remains terminal.

**Potential design requirements if this backlog item is prioritized (not implemented):**

1. Persist an immutable monotonic authorization generation/epoch (or an append-only revocation fact) scoped to the world, original source mapping and context. A nullable `updated_at` field by itself is not authoritative: it is mutable, can represent harmless metadata changes, and raw SQL can change status without updating it.
2. Intake captures the accepted authorization epoch on the interaction. A route deactivation advances the epoch _transactionally_, even when no outbox exists. A later reactivation never resets the epoch.
3. Response persistence, delivery preview, preparation, claim, preflight, reconciliation and operator commands reject an interaction whose accepted epoch predates the current epoch. During ambiguous delivery, evidence of an already sent message must still be recordable without initiating a new send.
4. Revoke/restore operations must serialize with route resolution and delivery claim under the established lock order. Explicitly test concurrent revoke-versus-send, repeat revocation, restore, revoked player identity and active-world changes.
5. Include a migration/backfill policy for existing interactions and mapping rows, migration drift audit, and a rollback strategy that never unlocks retired interactions. No change is authorized to deployed databases or the consumed Step 14 fixture by this document.
6. The safety acceptance test should expect **operator preparation to stay denied after restoring a route** for the historical interaction. The present reproduction test documents the current unsafe policy gap, not the intended final behavior.

**Disposition:** user clarified that DM removal of an individual NPC from a scene is rare and the response should simply not send. That is modeled by revoking the NPC’s M2.9 local-presence evidence, not by deactivating the entire Discord scene mapping. Revoked evidence stays invalid after a new grant; the old interaction must not be generated or delivered. SEC-01 refers specifically to the separate global route-deactivation/reactivation plus **explicit operator delivery** path, which has no automatic sender. Keep its regression test and document the risk, but defer epoch/schema changes unless operator workflow requirements demand them. This finding alone is no longer an M2.12 merge blocker; independent review and remaining safety gates still apply.


## DM-scene authority clarification (5 November 2026)

- **Removing an NPC from an RP scene** means revoking that NPC's local-presence evidence (M2.9) while preserving the shared Discord scene mapping. A player or DM may later bring the NPC back via fresh scene authorization, but an old interaction tied to revoked evidence does not inherit that new grant.
- **Disabling the entire Discord route** is an administrative channel/mapping operation, not equivalent to removing one NPC. This rare explicit-operator path is tracked separately as SEC-01 (deferred P2), not used to justify a migration in M2.12.
- The PG17 regression validates revoke-during-generation, new presence grant, old response replay refusal, operator preview/prepare denial, and zero fake sends. The full PR still needs final CI and independent audit before merge.
