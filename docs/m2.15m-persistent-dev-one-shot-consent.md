# M2.15M — persistent DEV-only one-shot NPC reply consent

## Product milestone

One **real visible Sentinel reply** in a freshly authorized, private
Living World DEV thread remains the next user-visible goal. M2.15L,
now merged, can verify the actual DEV PostgreSQL source and speech
policy, but only as a read-only preview.

M2.15M implements the **durable database part** of the send authorization
flow in a separate Draft PR. It DOES NOT create a live Discord sender,
a webhook, a model call, an authenticated DM registry or a public CLI.
No migration is to be applied to the owner's DEV DB under this milestone.

## Two distinct approvals — important correction to M2.15K

1. **Host scene speech policy**: issued **before** the player sends a new
   Discord event, valid for NPC presence and narrative speech eligibility.
   This already exists as `npc_scene_speech_policies` from migration 0018.
2. **One-shot response consent**: issued **after** a fresh authenticated
   original Discord message has been persisted, because its immutable
   Discord snowflake cannot be known in advance. It must bind exactly
   that event, the player, NPC, world, scene and original guild/parent/thread.
   This is what new migration **0019** stores.

The old M2.15K *unit-only* contract assumed an event-specific consent
could predate the original event. That assumption does **not** work for
a live operator. In M2.15M the **host speech policy** must predate the
event; the **event-specific one-shot consent** follows it.

## Schema and database guard

Migration `src/db/migrations/0019_dev_first_reply_consents.sql` and
matching Drizzle schema/snapshot/journal create the initially empty
`npc_dev_first_reply_consents` table:

- Exact foreign-key-bound world/NPC/scene/original interaction; exact
  mapped player entity and original Discord message/guild/parent/thread
- Fixed harmless reply `Acknowledged. Standing by.`
- Database-generated operator provenance and issue/claim/revoke clocks;
  time-bounded expiry of **at most five minutes**
- **Unconditional unique** `(world_id, source_message_id)` and
  `(world_id, interaction_id)` — survives revocation, completion or
  an uncertain outcome. New consent IDs cannot rearm one original event
- One terminal `approved -> claimed` or `approved -> revoked`
  transition; claimed/terminal records are immutable and never deleted.
  Attempt ID and claimed timestamp persist. No refund/no automatic retry
- PostgreSQL trigger checks exact database/role pairs
  (`living_world_gateway_dev/lw_gateway_dev` or
  `living_world_ci/living_world_ci`), existing received original
  Discord interaction and active eligible host scene speech policy.
  Foreign database roles, DELETE, TRUNCATE, replay and changed target
  are rejected at the DB boundary.

**No historical rows are backfilled.** The old consumed Sentinel event
is neither automatically authorized nor reused. Reapplying a consent
with a new UUID does not bypass unique constraints.

## Internal operator-only repository

`src/admin/dev-first-reply-consent.repository.ts` provides only three
internal functions: `issueDevOneShotConsent`,
`claimDevOneShotConsent`, and `revokeDevOneShotConsent`.

They require disabled Discord/outbound/LLM configuration, exact trusted
local DEV or disposable CI PostgreSQL role, strict source/route/actor
identities and the existing M2.15L real DB read-only preflight. They
lock the original interaction and conditionally claim an unexpired,
unclaimed record inside a PostgreSQL transaction.

**Claiming is a database event, NOT a send.** Every result has
`canGenerate=false`, `canSend=false`, `wouldSend=false`.
No host command to call these functions is exported in this PR,
and no live runtime component imports them. The `operator_entity_id`
is attribution, not independently authenticated Discord/DM consent.
That separate identity and one-time action approval must still be
designed, reviewed and authorized before a real send.

## CI acceptance and noninterference

- GitHub Actions runs migration **0019 only on disposable PostgreSQL 17**,
  never on the user's local `living_world_gateway_dev`.
- Unit tests reject forged caller flags, incomplete consent scope,
  enabled Discord/LLM configuration and raw error disclosure.
- Rollback-only PostgreSQL tests use the same original SDK-shaped
  synthetic inbound from M2.15I/L to exercise issuing a real DB consent,
  claiming it once, duplicate claim, attempted reissue with new consent,
  host revocation, forbidden target update/DELETE/TRUNCATE and full
  rollback to an empty consent table.
- The old migration 0018 preflight remains a **read-only legacy
  guard**, updated to pin the exact 0019 SQL and journal append so it
  still understands a reviewed migration history with 20 entries.
- Existing PostgreSQL, CI Quality Gate, isolated Gateway DEV and all
  security analyses must pass on the **exact final PR head**.

## Separate future approvals — not granted here

Before anyone applies migration 0019 to the owner's local DEV DB:
explicit owner permission, read-only pending-migration preflight,
verified current DB identity/migration history, a fresh valid backup
and reviewed apply/rollback instructions. **Do not run local migrate now.**

Before one real fixed-text Discord reply:
1. Fresh new private parent/thread and DEV world/player mapping/presence;
   pre-event host speech policy; never reopen the consumed inbound
2. A new live authenticated Gateway event *after* host policy issuance
3. An independently authenticated local operator who deliberately
   reviews/approves one original event; exact DB consent, atomic claim
4. Recheck of origin, route, host policy, current scene and the claimed
   attempt at the **actual HTTP send boundary**; no retry after uncertain
   result, strict target allowlist and audit/stop
5. Owner's separate explicit go/no-go for the one real harmless Discord
   send. Paid LLM response generation remains disabled until a
   different approved milestone.

The owner is Product Owner and practical tester; no manual coding is
expected. None of the remaining live actions is authorized by this PR.
