# M2.15A — Offline continuation after persisted Discord NPC inbound

**Status:** Draft PR; no live activity authorized.

## Evidence and reason for this slice

The sixth owner-authorized Sentinel DEV one-shot produced `message_matched`, `intake_accepted`, `post_write_audit_pass` and `npc_e2e_inbound_complete`. The read-only fixture preview is `already_used`, with one received interaction and zero deliveries ([Notion checkpoint §120](https://app.notion.com/p/40c013906e718156a0ddd55848536f0d)).

The existing M2.13B offline scene handshake starts by **ingesting a new message**. Re-entering a *persisted* event into M2.8 intake returns `duplicate` by design and must not be worked around by replaying the Gateway, resetting the DEV fixture or loosening deduplication.

This milestone adds `src/offline/npc-post-inbound.ts`: a test-only continuation port that starts from exactly one trusted, already persisted `received` event. It is **not** an operator script and is not imported into the app runtime, production Gateway, real provider or outbound CLI.

## Contract

1. Strict request shape: original source world, scene, message, guild, parent, thread, author, NPC and interaction identifiers. Caller-supplied identifiers are claims for lookup and matching, **not authorization**.
2. `received` must query a single DB event by original world/event/author; source binding is checked field-by-field, including source mapping, speaker, `received`, `unknown` communication mode and null presence. Zero/multiple matches fail closed.
3. Required `authorize` port independently re-checks the original mapped player and **current** scene/Discord route authorization in the DB. A revoked user mapping or changed route blocks continuation; asserted player/DM privileges never count.
4. `presence` reads trusted local-presence evidence. `prepare` must be the existing M2.9 `prepareLocalInteraction` transactional boundary: it revalidates evidence, NPC location/version, scene policy, source-event time and revocation. No presence is granted from the player's message.
5. Only successful `prepared` continues to the existing fake-only M2.12 response/delivery harness (M2.7 generation + M2.10 outbox) in disposable `delivery-test-<UUID>` worlds. Provider is synthetic, delivery is in-memory; the fake ACK is not a Discord acknowledgement.
6. Exact `NODE_ENV=test` is required, with Discord runtime/outbound disabled and non-OpenAI provider. No retry on error; an exception after response begins is treated as uncertain.
7. A fixed-category diagnostic outcome never exposes message bodies, IDs, secrets, SDK objects or database exceptions. It cannot alter the state transition.

## Verification

- Unit tests cover source binding, strict request shape, replay refusal, current author/route authorization, missing/revoked presence, failed transactional preparation, uncertain outcomes, environmental gates and diagnostic privacy.
- Real PostgreSQL integration tests use the existing isolated fixture, actual M2.8 intake once, actual M2.9 preparation, actual M2.7 response and M2.10 delivery repository, **only fake LLM and fake transport**; prove one persisted event can yield exactly one fake ACK without re-ingestion, while revoking player mapping, original route or NPC presence fails closed.
- No schema migration, fixture reset, live Gateway session, Discord POST, production runtime wiring, paid model call or real owner DEV database write.
- CI gate required before review: TypeScript, lint, Prettier, unit suite, PostgreSQL 17 integration, isolated Gateway DEV CI and security checks.

## Important limitations / next decision

This is not a new production service and does **not** make the consumed Sentinel event eligible for a live response. The real-world policy for turning a past stored `received` event into an NPC utterance, a safe local-readiness/preflight, NPC persona/output review, outgoing identity and an **independently approved single outbound delivery** must be designed and separately approved before sending any message.

Preserve the original `lw-dev-npc-e2e-001` fixture and its single audit record. Do not re-arm it, grant new presence, alter routes, enable outbound, fetch privileged Discord data, run a live Gateway or invoke a paid LLM under this milestone.
