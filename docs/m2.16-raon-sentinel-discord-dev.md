## Run from the owner’s Mac

Prerequisites are Node.js 22, pnpm, local Docker Desktop, the existing DEV bot token in `.env.gateway-smoke.local`, the mapped test user's ID in `.env.gateway-player.local` (key `LW_PILOT_TEST_USER_ID`), and the existing SSH identity for Hetzner. Run all Mac commands from the root of the existing Living World checkout. Switch to the reviewed PR branch there so the local private env files stay in place.

```bash
cd "$(git rev-parse --show-toplevel)"
git fetch origin feat/m2-16-raon-sentinel-arm64-probe
git switch feat/m2-16-raon-sentinel-arm64-probe
git pull --ff-only
pnpm install --frozen-lockfile
```

If the branch has never been checked out, use `git switch --track origin/feat/m2-16-raon-sentinel-arm64-probe` after fetching.

### 1. Use the existing inference process

On the Mac, set `RAON_SSH_HOST` to the existing VPS IP or SSH hostname from the [Hetzner checkpoint](https://app.notion.com/p/3fe013906e7181b485caf5af512b8494). The account is `livingworld`.

```bash
ssh -i ~/.ssh/living_world_hetzner "livingworld@${RAON_SSH_HOST:?set the existing VPS host}"
curl -fsS --max-time 5 http://127.0.0.1:8000/health
```

If the check succeeds, leave the existing process running. If it is down, check port 8000 and use the previously built executable and already cached model on Hetzner. The original probe used `~/raon-llama.cpp`; if your build lives elsewhere, change only the working directory. If the existing model is in a separate local file, replace `-hf …` with `-m /absolute/path/to/the-existing.gguf`. Stop and inspect if a different process already owns the port.

```bash
ss -ltn 'sport = :8000'
cd ~/raon-llama.cpp
./build/bin/llama-server \
  -hf KRAFTON/Raon-1-nano-gguf:Q4_K_M \
  --host 127.0.0.1 --port 8000 --alias Raon-1-nano \
  --ctx-size 4096 --threads 2 --parallel 1 \
  --reasoning off --chat-template-kwargs '{"enable_thinking":false}'
```

In a separate Mac terminal, keep this tunnel open. If using a new shell, set `RAON_SSH_HOST` there too.

```bash
ssh -i ~/.ssh/living_world_hetzner -o ExitOnForwardFailure=yes \
  -N -L 127.0.0.1:18000:127.0.0.1:8000 \
  "livingworld@${RAON_SSH_HOST:?set the existing VPS host}"
```

Verify from a third Mac terminal.

```bash
curl -fsS --max-time 10 http://127.0.0.1:18000/health
```

### 2. Prepare the isolated Discord route and DEV database

In the existing private DEV guild, create one dedicated parent text channel and one Public or Private Thread. For a Private Thread, add the existing DEV bot and the single test player as thread members. Public Threads use the parent channel's access permissions. The bot needs View Channel, Read Message History, and Send Messages in Threads on the parent. Each eligible turn uses a literal bot mention. Stop any other local Living World Gateway using this bot.

Keep `DISCORD_ENABLED=false`, `DISCORD_OUTBOUND_ENABLED=false` and `LLM_PROVIDER=disabled` in the base DEV env. Populate `LW_DEV_GUILD_ID` in `.env.gateway-dev.local` with the DEV guild ID. Create `.env.raon-dev.local` with private permissions and the following nonsecret settings, replacing the two Discord IDs.

```dotenv
LW_RAON_PARENT_ID=<new parent text channel ID>
LW_RAON_THREAD_ID=<new private thread ID>
RAON_BASE_URL=http://127.0.0.1:18000
RAON_CONTEXT_TOKENS=4096
LLM_MODEL=Raon-1-nano
LLM_TIMEOUT_MS=30000
RAON_DEV_OUTPUT_TOKENS=192
```

Use the existing DEV volume with migration 0019 already applied. For a brand new volume, follow [isolated Gateway DB setup](gateway-dev-local-db.md). A populated volume missing 0019 should follow the [0019 handoff](m2.15n-migration-0019-read-only-handoff.md). This pilot introduces no migration.

```bash
docker context show
docker compose --env-file .env.gateway-dev.local -f compose.gateway-dev.yml up -d --wait
node --env-file=.env.gateway-dev.local --import tsx src/admin/gateway-dev-db.ts check
pnpm admin:raon --prepare
```

`--prepare` verifies the exact database identity and prepares or reuses the same route, NPC, player mapping and presence. It writes only to the dedicated synthetic world `lw-dev-first-reply-raon-001`. It performs no inference and opens no Discord connection. `--check-raon` optionally checks the template, tokenizer, schema response and usage against the running model without Discord. The same check runs at each session startup.

### 3. Optional NPC persona transport

In the dedicated DEV parent text channel, an operator can create an incoming webhook using Edit Channel → Integrations → Webhooks. Set its default avatar to Sentinel's portrait if desired. Copy the webhook URL into the existing private `.env.raon-dev.local` as `LW_RAON_NPC_WEBHOOK_URL`. Treat the URL as a credential; never commit or share it. The bot does not create webhooks or require Manage Webhooks permission.

With this setting, the runner checks the webhook's exact guild and parent channel at startup and again before each send. Responses are sent in the configured thread as **Sentinel-001**, using the canonical fixture name, not model-provided identity. This uses the webhook's default avatar for now. The native typing indicator still belongs to the bot. Discord incoming webhooks do not support native reply references or nonce enforcement; source linkage remains in the durable outbox, and uncertain sends are never retried. The existing bot-native reply mode remains available only when the setting is omitted. No silent fallback on webhook failure. Public-thread persona delivery is covered by a simulated regression; live/private webhook compatibility is not yet verified.

### 4. Play and stop

```bash
LW_RAON_SESSION_APPROVED=true pnpm admin:raon --run
```

Wait for `{"event":"raon_session","outcome":"ready"}`. In the configured thread, select the real Discord mention for the Living World bot and send **@Living World [Sentinel] Introduce yourself and explain your duty.** Repeat the mention and `[Sentinel]` or `[Sentinel-001]` on subsequent turns. With the persona webhook configured, Sentinel's generated speech appears under the Sentinel-001 author in the thread; otherwise the existing bot account posts it as a native reply to the source message. Wait for each reply during the first exploratory run. After source and ACL prechecks pass, Discord displays the native bot typing indicator; the runner refreshes it approximately every seven seconds while processing and stops refreshing at completion, failure or cancellation. Typing failures are nonfatal and never replace the actual reply.

Press **Ctrl+C** in the session terminal to stop intake, cancel queued work and revoke the session policy. Wait for `raon_session / stopped` before closing the SSH tunnel with **Ctrl+C**. Stop the inference server only if you started it for this trial. The DEV session has no elapsed-time or turn-count stop. Stop it manually with Ctrl+C (or SIGTERM); failures still stop safely when required. While running, the owner-local runner rotates its 30-minute host speech policy every 20 minutes on the serial dialogue queue, preserving conversation history and retaining the existing database expiry guard. A revoked or failed policy renewal stops the session instead of silently reopening an externally revoked policy. A source created during rotation may fail closed; send a fresh mention if that happens. The DEV database remains available for reviewing evidence. If delivery is marked `uncertain`, check the thread before asking the next question. The session never replays the source event.

## Context, accounting and boundaries

| Template field                           | Persisted mapping or pilot behavior                                                                                                                                                                                      |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Identity and alias                       | NPC core, validated baseline profile and world-scoped `Sentinel` alias                                                                                                                                                   |
| Personality, duty, background and goals  | Baseline identity, traits, values and brief summary                                                                                                                                                                      |
| Capabilities, narrative weight and stats | Existing capability/game-profile records, simulation depth 1, weight 10, stat depth 0                                                                                                                                    |
| Location, state and availability         | Observation Post A, certain colocated state, active local presence and bounded host speech policy                                                                                                                        |
| Scene facts and observations             | Operator-authored state summary contains gate CLOSED and alert LOW, the verified observation of a blue crate, and explicit unknowns about delivery time, courier and the sealed room                                     |
| Restricted knowledge                     | Source-linked restricted fixture claim. Generic visibility filtering withholds the knowledge projection and keeps excluded text for response validation only                                                             |
| Dialogue and continuity                  | Up to three recent pairs from successfully acknowledged replies in this session, scoped to the same NPC, player and route. Interactions and outbox persist; continuity resets on restart                                 |
| Autonomy, relationships and memories     | Dialogue only. Existing memory and relationship records stay withheld where runtime lacks reliable exposure/disclosure evidence. No durable memory synthesis, further relationships, remote communication or tool access |

Source and route checks include the authenticated bot, private thread membership when applicable, current Discord permissions, source message, mapped player, unexpired two-minute source window, route revision, scoped host policy and NPC presence. The existing claim, persistence, outbox and acknowledgement path owns delivery. The bot transport makes at most one POST per attempted source. Outbound mention notifications are suppressed.

Raon is selected only inside this owner-local runner. It uses KRAFTON's OpenAI-compatible Chat Completions with a single speech field, thinking off, and template-aware tokenization via `/apply-template` and `/tokenize`. The provider compares actual returned usage with the exact rendered token count. It drops recent history if needed and checks the mandatory context again before inference. The active limit is 4096 total tokens with 192 reserved for completion by default. The existing 30-second generation timeout covers tokenization and generation. Usage telemetry has no monetary ledger entry for Raon. OpenAI’s paid budget and usage accounting remain separate.

Diagnostics are newline-delimited JSON. `raon_queue` reports waiting time. `raon_typing` reports initial typing or failure; `raon_policy` reports policy rotation or a blocked startup/renewal. `raon_persona` identifies the selected delivery mode without exposing credentials. `discord_intake`, `raon_presence`, `raon_npc_resolution` and `npc_response` report intake, resolution, context size, validation and persistence outcomes. `raon_generation` reports model, tokens, inference time and failure classification. `raon_delivery` and `raon_turn` report delivery and end-to-end processing time. Save the sanitized stream locally if you want a record, for example with `2>&1 | tee raon-dev.log`.

## Automated evidence

The local quality gate passed 935 unit tests, eight security checks, three standalone probe tests, type checking, lint, formatting and build. PostgreSQL 17 passed 347 tests, with one environment-specific test skipped in that suite. The PostgreSQL regression is parameterized for Public and Private Threads, checks typing and policy rotation with retained history, and uses simulated Raon and Discord HTTP to cover ten consecutive turns, restricted context, duplicate and unrelated events, ACL denial, tunnel failure, policy revocation and uncertain delivery. The owner-style local DB smoke used the dedicated non-superuser DEV role, migrated a disposable database and verified that running `--prepare` twice produced one world and zero inbound interactions.
