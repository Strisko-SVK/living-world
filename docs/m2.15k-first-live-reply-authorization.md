# M2.15K — disposable one-shot owner-consent contract

## Why this exists

The next product success in Notion document 11 section 73 is one **real,
owner-visible Sentinel reply** in a private DEV scene. M2.15J's read-only
preflight is merged; a positive preview is not operator consent or permission
to send. M2.15K provides a deliberately test-only rehearsal of the missing
one-shot consent/claim behavior before we build a real pilot entrypoint.

The fixed first reply is `Acknowledged. Standing by.`; a paid LLM request
is not necessary to demonstrate a live Discord reply.

## Contract rehearsed offline

`createOfflineOneShotPilot` in `src/offline/npc-one-shot-consent.ts`:

- Operates only inside Vitest when `NODE_ENV=test`,
  `DISCORD_ENABLED=false`, `DISCORD_OUTBOUND_ENABLED=false` and
  `LLM_PROVIDER=disabled`.
- Accepts an exact typed scope: world, NPC, scene, original interaction,
  mapped player, original Discord message, guild, parent and thread.
  Unknown flags (`execute`, `dm`, `ownerApproved`) are rejected.
- Requires the existing M2.15J `fake_only_candidate`, with every real-action
  flag false, plus a separate trusted host-operator consent record. The
  record must bind the exact scope and fixed text, be non-revoked, have a
  maximum five-minute validity and precede a fresh source event. The source
  event must be no older than two minutes.
- Calls an injected `claimOnce` port to consume an attempt **before**
  invoking any fake transport. The unit-test double is an in-memory atomic
  set; it ensures simultaneous attempts cannot both win.
- Rechecks preview and exact consent after the claim. Revoked or replaced
  consent, a changed route/policy or expired eligibility blocks fake
  continuation; the claim is not refunded.
- Runs only an injected fake transport. Acknowledged, confirmed not-sent,
  uncertain and thrown/ambiguous results consume the single attempt.
  No automatic retries or second send. Error results contain only fixed
  diagnostic labels, never event content, Discord IDs, SQL or secrets.
- **Every output** has `readOnly=true`, `canGenerate=false`,
  `canSend=false` and `wouldSend=false`. Even `fake_ack` is no claim
  that a real send has happened.

There are no production imports, Discord client, webhook, LLM API, database
connection, migration or runtime entrypoint in this milestone. The consent
record and atomic claim are *test doubles*; they do not provide durable
authentication, a transactionally safe persistent latch, or real HTTP
authorization. This PR cannot be connected to a real send without new,
independently reviewed code and approval.

## Automated acceptance tests

Unit tests cover exactly bound actor/scene/route/source and fixed text,
forged permissions, non-host/expired/revoked consent, invalid snowflakes,
future/stale events, overlong consent windows, concurrent claims, replay,
revocation/replacement after claim, failed/uncertain transport without retry,
ambiguous claim outcome, disabled external services and sanitized errors.

The existing PostgreSQL integration and Gateway DEV tests must remain green.
No owner-local DEV fixture, original consumed Sentinel event or real network
resource is touched.

## Concrete next cutover to a visible DEV reply

Before requesting permission for the **single real Discord send**, implement
and review a separate, narrowly scoped live-pilot entrypoint:

1. An authenticated local operator identity and **durable** scoped one-shot
   approval/attempt record in PostgreSQL. A database migration and any
   owner-local application require separate approvals and verified backup.
   `issuedByEntityId` alone is attribution, not host authentication.
2. New private DEV thread/scene plus one fresh original SDK-authenticated
   player message *after* presence, host speech policy and operator consent
   are established. Do **not** rearm or reuse the consumed Sentinel inbound.
3. An operator dry-run reporting exact target, source event and policy
   validity without sending or writing an outbound response.
4. One fixed-text send through the existing reviewed Discord outbound
   allowlist/rate-limit transport with fresh database fences at the
   **actual** HTTP side-effect boundary, and one attempt even if HTTP/ACK
   is uncertain; independently authorized stop and audit.
5. A separate explicit owner authorization for each persistent DEV
   migration/setup, live Gateway connection and one real Discord send.
   Paid LLM interaction is a later gate after fixed-text delivery succeeds.

**Acceptance for the first live pilot** is visual: the owner types one
allowed real message in the private DEV thread, Sentinel replies once with
the fixed text in that same thread, and audit confirms no unauthorized
reply, duplicate, leak or retry. Until these gates are implemented, all
claims of real-send readiness remain false.

This PR stays Draft until exact-head Quality Gate, PostgreSQL 17, Gateway
DEV and security checks pass and it receives an independent technical
review. It may be squash-merged only after separate owner approval.
