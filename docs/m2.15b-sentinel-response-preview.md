# M2.15B — Read-only preview of the consumed Sentinel inbound

**Scope:** Offline operator diagnostics and regression tests. Draft only; no
live Discord connection, outbound, generation, database mutation or migration.

## Why

The owner-approved sixth Sentinel DEV one-shot persisted exactly one authorized
`received` interaction and zero deliveries. M2.15A proved synthetic
continuation with fake generation and fake delivery in PostgreSQL CI.

The existing readiness preview correctly reports `already_used`, but that
status must **never** imply authorization to generate or send an NPC reply.
Before planning the first outbound, we need a separate **read-only** view of
the actual persisted event's integrity and NPC narrative availability.

## Contract

1. The operator CLI accepts only `--preview` (or no arguments) and checks the
   previously approved private DEV database/environment and the exact
   Sentinel world/scene/route. Normal Discord runtime, outbound and real LLM
   remain disabled. No Discord token is needed or printed.
2. The PostgreSQL transaction starts with `set transaction read only`.
   A strict PostgreSQL 17 database/role/non-superuser check and presence of
   the route-revision trigger precede every fixture/event query.
3. Reuse the already-audited M2.14C **post-write inbound invariants** for
   precisely one event: player mapping, NPC, world, scene, route, activation
   audit, local presence, source-event timing, literal authenticated bot mention,
   response/status still inert, and **zero outbound deliveries**.
4. Only then consult the existing trusted `readNpcSummonFacts` projection and
   `evaluatePlayerSummon` decision. Do not infer NPC activity/perception or
   concurrent scenes from location or player-written text.
5. Output only fixed-category status/availability/reason, never player IDs,
   source message IDs, request or response text, DB URL, tokens, raw SQL,
   model prompts or exception payloads. Invalid/altered evidence reports
   `integrity_blocked`, not which private check failed.
6. All preview outcomes have `canGenerate=false`, `canSend=false` and
   `readOnly=true`. Even a `candidate` is **not** authorization to generate
   dialogue or send in Discord. Distinguish unknown, delayed, unavailable and
   candidate-needs-owner-review.

## Expected owner DEV result

Because the current facts repository deliberately does not guess whether
Sentinel is free, aware of the player or active in another scene, the expected
result **if its stored inbound integrity is still valid** is:

```json
{
  "event": "npc_e2e_response_preview",
  "worldKey": "lw-dev-npc-e2e-001",
  "status": "needs_availability_review",
  "availability": "unknown",
  "reason": "activity_unknown",
  "canGenerate": false,
  "canSend": false,
  "readOnly": true
}
```

If an invariant has changed, expect a fixed `integrity_blocked` outcome or
`npc_e2e_response_preview_failed_safely`. Do not reset the fixture, grant
new presence or relax policy to force the preview to pass.

## Local read-only command after approved merge

Run only from the reviewed and merged main with the existing **private**
operator environment files. The command is local PostgreSQL-only; it does
not request MessageContent, connect to the Gateway or send anything:

```bash
node --env-file=.env.gateway-dev.local --env-file=.env.gateway-pilot.local --env-file=.env.gateway-npc-e2e.local --import tsx src/admin/discord-npc-e2e-response-preview.ts --preview
```

Do not paste .env contents, IDs, tokens or any raw message text. Share only
the fixed-vocabulary JSON result. This step is read-only, but it is **not**
permission to trigger a response for that consumed event.

## Evidence gate / follow-up

- Unit tests: strict preview-only arguments, hostile environment denial before
  DB connect, fixed redacted output, all availability states, mandatory
  `canSend=false` and read-only transaction ordering.
- PostgreSQL 17 integration: synthetic accepted inbound passes the real audit
  and reports unknown availability without modifying any row; before intake or
  after mapped-human revocation, it fails closed. Rollback-only synthetic world.
- All CI and security jobs must pass before requesting a merge.
- Later product design must specify DM-authorized availability and response
  content review. Player summons cannot teleport an NPC or override DM control.
  Explicitly approved outbound remains a **separate future milestone**.
