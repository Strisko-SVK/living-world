# M2.16 — Raon-1 nano on the EXISTING Hetzner ARM64 VPS (Sentinel probe)

Status: **isolated diagnostic only**. No new server, no additional paid infrastructure, no Discord send, no access to private data, no database migration and no permanent daemon.

## Verified infrastructure baseline (last SSH audit: 28 Oct 2026)

Notion [Hetzner ARM64 checkpoint](https://app.notion.com/p/3fe013906e7181b485caf5af512b8494): `living-world-prod-01`, Hetzner CAX21, ARM64 Ampere, four vCPUs, 8 GB RAM, 80 GB disk, Ubuntu 24.04 LTS, 2 GiB swap, Docker installed. The old audit had about 7.1 GiB RAM available. **That is NOT a current capacity check or proof the server is still unused.**

This probe must not bypass INFRA-02/03/04 gates for production deployment, backups or persistent data. Do not start the development `docker-compose.yml` on the VPS: it publicly maps PostgreSQL port 5432.

## Model/runtime

- Model: [KRAFTON/Raon-1-nano-gguf](https://huggingface.co/KRAFTON/Raon-1-nano-gguf), `Q4_K_M` (~2.08 GB weights), Apache-2.0 model weights.
- Runtime: [KRAFTON's `raon-1-nano` branch of llama.cpp](https://github.com/krafton-ai/llama.cpp/tree/raon-1-nano), using its `llama-server` OpenAI-compatible Chat Completions endpoint.
- **ARM64 CPU only** (no GPU expected). Begin at 4,096 context tokens, two CPU threads, one parallel request. Do NOT copy the manufacturer's 262,144-token context example to an 8-GB VPS.
- The model's thinking consumes output tokens; this diagnostic uses `max_tokens: 768`. Measure actual latency, memory, output completeness and quality instead of promising performance.

## Controlled manual trial, ONLY after re-checking current server resources

Run commands as the non-root host user. They are not executed by this PR. Keep the model separately from the existing `/opt/living-world` checkout and leave the service bound to loopback only.

```bash
free -h
df -h
sudo docker ps
git clone --depth 1 --branch raon-1-nano https://github.com/krafton-ai/llama.cpp ~/raon-llama.cpp
cd ~/raon-llama.cpp
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j 2 --target llama-server
./build/bin/llama-server \
  -hf KRAFTON/Raon-1-nano-gguf:Q4_K_M \
  --host 127.0.0.1 --port 8000 \
  --alias Raon-1-nano \
  --ctx-size 4096 --threads 2 --parallel 1 \
  --temp 0.1 --presence-penalty 1.5 \
  --reasoning on \
  --chat-template-kwargs '{"enable_thinking": true}'
```

The first run downloads model weights. Keep this in an interactive terminal and stop with Ctrl+C after the trial. If resources or server status are uncertain, test on the Mac first instead of risk to existing workloads. No public inference port or domain is needed.

From an **updated** checkout of this branch on the same host with Node.js 22+, or via an SSH port forward from the Mac to the host's local port 8000:

```bash
node --test scripts/raon-sentinel-probe.test.mjs
node scripts/raon-sentinel-probe.mjs --show-speech
```

If port 8000 is in use by another loopback service, choose another port for `llama-server` and set `RAON_BASE_URL=http://127.0.0.1:<port>` when running the probe. The probe rejects non-loopback URLs by design.

## Test coverage and privacy

The standalone probe sends three **synthetic** Sentinel-001 dialogue scenarios: greeting, unknown information, and unauthorized action/prompt injection. It reports latency and available token usage. `--show-speech` opts into printing synthetic model replies; without it, logs contain only scenario IDs and metrics. HTTP failures show a generic error, not raw provider bodies.

It does not use the Discord Gateway, real NPC identity mapping, DB, existing LLM budget ledger or outbound transport. The model cannot mutate the authoritative World State. It does **not** demonstrate live Sentinel conversation.

## Acceptance before NPC integration

1. Local offline tests pass with fake fetch and no external traffic.
2. ARM64 server build succeeds; the correct GGUF loads with no OOM or harmful swapping; existing services stay healthy.
3. All three scenarios produce one valid `{"speech":"..."}` object. Record real latency, tokens, RAM, CPU load and quality.
4. A DM reviews role consistency, unknown-fact handling and whether dangerous instructions were obeyed; test longer multi-turn RP separately.
5. Only after that, implement a gated `TextProvider` adapter for the Raon Chat Completions endpoint, including truthful token accounting, structured-output capability tests, budget/availability controls, world/scene scope checks and outbox safety. Do not turn `LLM_PROVIDER` on or send a live Discord response automatically.

No change to existing OpenAI Responses provider, no main/runtime wiring, no production deployment in this PR.
