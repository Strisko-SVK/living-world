# M2.14D — Fail-closed diagnostics for Sentinel first-contact inbound

**State:** Offline-only Draft PR, following M2.14C first live attempt in isolated
`lw-dev-npc-e2e-001`. A bot login succeeded
(`pilot_gateway_ready`), then the runner logged `pilot_gateway_stopped` and
`npc_e2e_inbound_failed_safely` without `pilot_gateway_received`.
The owner independently confirmed the test-world readiness remained
`ready_for_inbound` with **0 interactions and 0 deliveries**. No NPC action
was generated, and no test world or schema migration should be recreated.

## What was not proved

The previous output did not distinguish no Gateway `MessageCreate` event,
a rejected message shape, a stale/unauthorized intake, or a failed post-write
audit. Discord's public threads inherit visibility from their parent text
channel; public thread membership is not in itself required. A private
thread needs its own access. The existing one-shot filter deliberately
requires `ChannelType.PublicThread`, exact guild/parent/thread and the
owner-human direct bot mention. Screenshot presence in a server member list
is not proof of message delivery to the Gateway.

## New diagnostic stages

M2.14D preserves the exact one-message filter, 90-second timeout,
authentication guard, database checks, single-event latch, intake transaction,
and no-send/no-LLM boundary. It adds optional deterministic observer signals
to the proven transport and enables those signals **only in the new
Sentinel runner**, never in normal runtime or the consumed historical pilot.
No IDs, names, full messages, prompts, tokens, raw errors or SQL are printed.
The observer ignores unrelated guild/channel events and deduplicates
reports per run.

Example fixed-category output:

```json
{"event":"npc_e2e_inbound_diagnostic","stage":"target_thread_event_seen"}
```

The possible stages are:

- `target_thread_event_seen` — the expected guild and thread received a
  Gateway `MessageCreate`; no user text or identity is logged.
- `thread_shape_rejected` — parent or thread type (public only) differs.
- `sender_or_kind_rejected` — not the authorized human normal message.
- `message_normalization_rejected` — SDK message was not parseable.
- `mention_rejected` — missing or extra literal bot mention.
- `exact_text_rejected` — the scripted request text did not exactly match.
- `alias_rejected` — the Sentinel alias parser did not accept it.
- `message_matched` — passed the strict no-write Gateway filter.
- `intake_accepted` — one interaction may now be durably stored.
- `intake_rejected`, `intake_failed` — the interaction was not accepted;
  run read-only readiness before any decision.
- `post_write_audit_pass` or `post_write_audit_failed` — read-only
  verification of exactly one inert accepted event.
- `timeout_without_match` — 90 seconds elapsed without an eligible event
  (other observed filter stages identify why, if the exact thread was seen).
- `timeout_during_processing` — a matching event was claimed but work was
  still in progress when the deadline fired.
- `gateway_interrupted`, `operator_interrupted` — connection/signal
  stopped the session.
