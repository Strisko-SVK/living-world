# M2.15I — one ingress, one fake NPC ACK (offline only)

## What this closes

M2.15H used a second directly inserted test interaction for the response/outbox
phase, because PostgreSQL `now()` tracks the enclosing transaction start.
M2.15I uses **one original interaction** all the way from a fake
`discord.js` `MessageCreate` event through normalization, strict
`createDiscordIntake` and PostgreSQL persistence, local-presence preparation,
existing response claim/context/generation, fake transport and one durable ACK.

The injected `EventEmitter` Discord client has a fake login/destroy function.
It does **not** authenticate with Discord or receive an actual Gateway message.
The event ID and human ID are explicitly synthetic CI-only test data; do not
describe this as a live authenticated Discord request.

## Receipt-clock correction

The `createInteraction` repository records `createdAt = clock_timestamp()`
for Discord-sourced interactions, rather than the transaction-start default. This stores the real database insertion/receipt
instant even in a long-running enclosing transaction. It does not trust a
caller-provided timestamp. The independent, immutable Discord snowflake
timestamp and M2.9 pre-existing-presence/route checks remain mandatory.
Non-Discord interactions keep their existing timestamp semantics. No schema
change, migration or relaxed validation is needed.

## Automated evidence

The rollback-only disposable PostgreSQL 17 Sentinel fixture checks:

- One SDK-shaped `MessageCreate` goes through the existing normalized
  thread route and strict mapped-player/alias intake, using a trusted bot ID
  supplied by an injected fake client, **without any network connection**.
- One stored, original interaction has its database receipt after host
  speech-policy issuance. `readVerifiedOfflineSpeechPhaseSnapshot` checks
  `received -> prepared -> dispatched -> responded -> sending` against the
  same interaction.
- The existing fake provider generates strict validated JSON speech, the
  existing response/outbox store persists it, and a fake delivery transport
  records precisely one ACK with the original Discord destination.
- A route revision just before the fake provider call blocks generation
  without invoking the provider; the negative change rolls back.
- Host approval revoked after outbox preflight blocks the fake transport
  before its send call; this negative change also rolls back.
- A repeated workflow attempt is ineligible; no second fake send is recorded.
  A nested SAVEPOINT rollback removes response/outbox changes, and the
  outer fixture rolls back every synthetic record.
- The fake Message has neither `reply()` nor `channel.send()` invoked.
  No tokens, live Gateway, webhook, provider API, owner DEV database or
  deployment are used.

## What it does NOT prove or authorize

This is not a live Discord SDK-authenticated inbound test: the client and
event are deliberately injected. It also does not prove that a fresh
operator-approved event can be sent over the real Discord HTTP boundary.

Before the first live private DEV reply, separately design and verify:

1. Owner-scoped, time-limited, one-shot pilot approval and an authenticated
   operator identity, not a user-asserted DM role.
2. Actual fresh inbound event after authoritative NPC presence and host
   speech approval, exact user/world/scene/thread/alias/route revision.
3. Revalidation at real generation and outbound network boundaries,
   including policy expiry/revocation, current presence, outbox lease and
   fail-closed uncertain delivery; **no automatic retry**.
4. A read-only/no-send preview and an independently approved harmless
   predetermined first send, with abort/stop and audit. Real LLM quality
   evaluation is a later, separately approved stage.

Do not reuse or rearm the owner's consumed Sentinel inbound. This PR may
be reviewed and run in synthetic CI but must stay Draft pending a distinct
owner squash-merge decision. No change to the owner's 0018-applied database.
