# M2.15O — First owner-visible Sentinel reply (DEV only)

Status: **offline code Draft PR only**. This handoff is not permission to merge,
write the owner's DEV database, connect a live Discord Gateway, use Discord REST,
send any message, deploy or call a paid LLM. Source: Notion doc 11 §§160–161,
[Issue #51](https://github.com/Strisko-SVK/living-world/issues/51).

## Scope

- Only new isolated `lw-dev-first-reply-001`; never the consumed NPC E2E
  world/event.
- One new private Discord DEV parent/thread, supplied via **local private**
  environment (IDs are not committed).
- One mapped test human and `Sentinel-001`; other real campaigns untouched.
- One original authenticated SDK `MessageCreate`, received only **after**
  the pre-event host scene speech policy.
- One fixed reply **exactly** `Acknowledged. Standing by.`, sent by the
  Living World DEV bot user as a reply to that original message.
- No paid LLM. No webhook setup or cross-thread fallback.
- Every real/persistent stage requires a **separate explicit owner approval**.

- `LW_FIRST_REPLY_GUILD_ID`, `LW_FIRST_REPLY_PARENT_ID`,
  `LW_FIRST_REPLY_THREAD_ID`: new owner-supplied route (no old pilot IDs)
- `LW_FIRST_REPLY_PLAYER_ID`: actual consenting test human Discord user
- For independently approved Gateway **only**:
  `LW_FIRST_REPLY_GATEWAY_APPROVED=true`
- Only with separately approved privileged content intent:
  `LW_FIRST_REPLY_PRIVILEGED_CONTENT_APPROVED=true`
- For separately approved fixed-text send **only**:
  `LW_FIRST_REPLY_SEND_APPROVED=true`,
  `LW_FIRST_REPLY_OPERATOR_KEY_PATH` (absolute, outside Git),
  `LW_FIRST_REPLY_OPERATOR_UID` (actual local OS UID)

`DISCORD_ENABLED=false`, `DISCORD_OUTBOUND_ENABLED=false` and
`LLM_PROVIDER=disabled` remain required; the dedicated operator commands
do not start the normal runtime or use the generic webhook dispatcher.

The operator key is an independent 32-byte random hex secret owned by the
invoking local OS account, with exact 0600 permissions and no symlink/hardlink.
Create it **only on the owner's machine when the operator setup is approved**.
Never store it in Git, Notion, command-line arguments, logs or chat.

## Operational critical path (only after the relevant approvals)

1. Verify local main/DB identity and migration 0019 `already_applied_verified`.
   No migrator. Check private Docker context and backup custody.
2. Verify the new parent/thread ACL, bot read visibility and
   `SEND_MESSAGES_IN_THREADS` permission before activation. Discord checks
   require separately approved live metadata reads; no such calls in offline CI.
3. Run fresh provisioning preview, then **separately approved** prepare:
   `--prepare --confirm-world lw-dev-first-reply-001 --confirm-parent <PARENT>
   --confirm-thread <THREAD> --confirm-database living_world_gateway_dev --offline-only`.
   It atomically creates the default-deny fixture, maps one human, gives
   Sentinel current location/presence, enables mapped-player intake, and issues
   a host policy valid at most 30 min. No rearm of an existing world.
4. Run Gateway read-only preflight; separately authorize one inbound Gateway
   with `--connect --confirm-world lw-dev-first-reply-001 --confirm-guild
   <GUILD> --confirm-parent <PARENT> --confirm-thread <THREAD>
   --confirm-database living_world_gateway_dev --inbound-only --one-message`.
   The player sends one **fresh literal** message tagging the DEV bot:
   `@Living World [Sentinel] Report readiness.` (real user mention, not plain
   text). The Gateway accepts only the exact new thread/human, then stops.
   If content is not available, the privileged intent is another approval.
5. With a **separate** owner send approval, run the read-only first-reply preview
   on this one original event. The owner copies its Discord message snowflake.
   Issue the send CLI with exact route/source and fixed text:
   `--send --confirm-world lw-dev-first-reply-001 --confirm-guild <GUILD>
   --confirm-parent <PARENT> --confirm-thread <THREAD>
   --confirm-database living_world_gateway_dev
   --confirm-source <ORIGINAL_MESSAGE_ID> --confirm-reply
   "Acknowledged. Standing by." --one-shot --no-retry`.
   The operator must type the source-bound confirmation locally.
6. The authenticated operator command checks DB source and host policy, gets
   actual bot identity, parent/thread metadata, computed thread permissions
   and original Discord message **before** the claim. It then atomically issues
   per-event consent, claims once, and records a `sending` outbox attempt.
   Immediately before one POST, it rechecks fresh Discord metadata and
   claimed/policy/route data. Request uses fixed body, empty allowed mentions,
   source message reference and enforced nonce. **No automatic retries.**
7. After an exact ACK, durable outbox is `delivered` and source interaction is
   recorded as responded. After any ambiguity, terminal `uncertain` or
   `blocked` remains. A process crash leaves a durable `sending` attempt,
   which MUST be treated as uncertain. Never replay, reissue, retry, migrate,
   remove old state, or resurrect that source. Investigate visual Discord
   evidence without posting another message.
8. Stop; verify exactly one correct reply in the original thread and audit
   only sanitized status. Independently approved emergency disable can close
   intake and revoke host permission. No LLM rollout under this approval.

## Offline test coverage

- Deterministic fixture/activation tests with exact environment/route gates.
- Isolated SDK inbound arguments, distinct new route and privileged-intent opt-in.
- Local OS operator key and 0600/symlink/UID enforcement.
- Fake REST GET identity/parent/thread/ACL/original-event checks,
  fixed message_reference body, no-mentions and **zero retries** on 429,
  5xx, lost ACK or forged ACK.
- Disposable PostgreSQL 17 rollback-only setup/consent/claim/audit/stop test.

The live Discord route/ACL, source and transport **cannot be proven by CI**;
they are part of the later separately approved DEV pilot. Never call an offline
unit/PG PASS a live Discord success.

## Exit criterion

One and only one correctly routed, owner-observed bot reply
`Acknowledged. Standing by.` to the one authenticated new Sentinel request,
without duplicates, unauthorized sends, cross-thread leaks or paid inference.
