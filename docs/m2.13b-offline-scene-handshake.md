# M2.13B — Offline scene handshake, first engineering slice

**Status:** Draft, offline-only. This slice intentionally does not implement live DM controls, automatically summon NPCs, change the Discord intake grammar, enable bot runtime or grant any scene presence.

## Product rule being protected

Living World has **one Discord bot transport identity**. Fictional NPC identities are selected by the application within an authorized world/scene; players and DMs should ultimately be able to address NPCs naturally without creating Discord memberships or static NPC-per-thread mappings. Only the bot itself needs effective Discord channel/thread visibility. The historical Step 14 `[Sentinel]` grammar and one-human one-message controls were safety fences, not the permanent product contract.

An NPC is not authorized to speak merely because the player typed its name. DM world authority and NPC availability require trusted evidence and explicit rules. Do not derive operator/DM privileges from content, roles asserted in incoming payloads, or a language model.

## Implemented in this slice

`src/offline/npc-scene-handshake.ts` provides a **test-runner-only coordinator** around the existing, independently enforced boundaries:

1. Validate a fixed synthetic message/world/context source envelope and reject unknown asserted privileges.
2. Call the real M2.8 intake through an injected adapter (future test composition root): authorization, unique NPC alias, route/policy and identity must be verified transactionally by the existing intake implementation.
3. Look up exactly one immutable received interaction by world and source event. Re-check bound world, scene, author mapping, NPC UUID, Discord message/guild/channel/thread and route mapping before proceeding.
4. Resolve **existing** local presence evidence via a trusted database adapter. Do **not** auto-grant it to a player.
5. Ask the real M2.9 `prepareLocalInteraction` transaction to validate same-world/scene evidence, location, state version, source timestamps and policy. Only an actual fresh `prepared` result proceeds.
6. Call the existing fake-only M2.12 workflow for response and delivery. No auto retry after duplicates, errors, lost ACK, revocation or partial persistence.

`src/offline/npc-scene-handshake.test.ts` exercises guard behavior with injected fakes. Negative tests cover replay, conflicting world/scene/route, wrong source event, missing/multiple interactions, absent presence, blocked prepare, changed grant, uncertain delivery and dependency errors.

## Safety and remaining work

This slice now has **direct real-PostgreSQL intake composition tests** in `src/db/response-delivery.db.test.ts`. A disposable `delivery-test-<UUID>` world starts with an authorized synthetic player, trusted NPC presence, and **zero received interactions**. Only when the offline coordinator runs does its injected intake adapter invoke the actual M2.8 transaction-backed Discord intake. The coordinator then retrieves the real persisted interaction, validates the existing M2.9 presence/prepare transaction and executes M2.12 fake-provider/fake-transport response delivery. Tests cover exactly one original-scene fake ACK, duplicate message rejection, revoked presence, an unauthorized/unmapped player and concurrent intake handlers. **This remains test-only composition, not live Discord or a production composition root.** The intake adapter is injected with a synthetic event, not connected to a Gateway; true DM authorization and dynamic summon rules remain separate work.

Important unresolved issue: In a real delivery flow, unexpected exceptions after a send attempt must not be mislabeled as a safe retry. The result here deliberately returns a terminal ambiguous failure; no automatic re-execution is permitted. Final operator recovery remains separate.

**M2.13B next slice:** verify runtime adapter authentication and source-event binding before any live integration. Separately design world-scoped DM authority, read-only private NPC whereabouts, explicit DM force placement and NPC availability for natural player summons. An alias or caller-asserted privilege never grants presence.

**No authorization:** merge, deployment, owner-local DEV DB apply, new Discord channel/thread creation, live Gateway connection, real Discord send or paid LLM. Consumed Step 14 pilot remains untouched.

## Durable Discord route revocation fence (M2.13B safety hardening)

Migration `0017_discord_route_revision` records a database-managed route revision
timestamp whenever a Discord mapping's authoritative fields change, including
direct SQL `inactive -> active` status changes. On migration it resets existing
mapping revisions to the migration time because their previous history cannot
be verified; pending responses from before the upgrade fail closed.

The M2.10 delivery repository checks the route's latest revision against both
the immutable interaction receipt timestamp and the Discord Snowflake source
timestamp, using PostgreSQL microsecond precision. If the mapping changed after
the source event, both automated and explicit operator sends are blocked even
when the exact same mapping was later restored. The route check is run again
at preparation, claim and preflight, without a new cross-locking trigger on
interaction/outbox records. Existing uncertain delivery reconciliation stays
separate: an ACK can still be recorded as delivered, but cannot create a
second automatic send. This revision fence does not replace live Gateway
authentication or Discord external membership verification.

**Deployment impact:** migration is committed for review and CI only. No
owner DEV database is modified. Running it on a database would invalidate
pre-migration pending source replies; schedule this deliberately only after
separate owner approval for merge/deployment/migration.


## Offline SDK Gateway binding (test-only composition)

`src/offline/npc-scene-gateway.ts` derives a source envelope exclusively
from the normalized adapter message and its resolved DB scene. The bot ID is
supplied by the Discord adapter callback (from `client.user.id`), not by the
message, a player, or a world-scoped NPC record. The bridge rejects missing
literal authenticated-bot mentions and untrusted or ambiguous scene lookups.
Unknown asserted role/scope fields are ignored by the incoming schema; the
existing real M2.8 intake and M2.9 presence checks remain authoritative.

New unit tests cover bot-identity substitution, missing literal mention,
invalid message IDs, caller-asserted DM/scope fields, ambiguous scene lookups
and database intake denial. A new PostgreSQL integration test invokes the
actual `createDiscordAdapter` event callback with a synthetic SDK Message,
a fake EventEmitter-backed Client with stubbed `login`/`destroy`, real
transactional M2.8 intake and M2.9 local preparation, and M2.12 fake LLM
and fake outbound transport. It confirms one source-scene fake ACK only.

The test does **not** authenticate a real Discord session, exercise network
Gateway traffic, grant NPC presence, or enable production response runtime.
The actual runtime currently wires intake without this coordinator. Live
Gateway composition, real member visibility and send authorization still
require separate security review and explicit owner approval.
