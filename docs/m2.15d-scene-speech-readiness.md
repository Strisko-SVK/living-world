# M2.15D — Bounded scene-speech approval contract (offline)

**Status:** Draft implementation, **test-only**, not connected to the live
Discord runtime, real LLM or delivery worker. No migration or DEV DB writes.

## Current evidence

The owner ran the merged M2.15C Sentinel read-only preview. It returned
`direct_in_scene`, `needs_review`, `activity_unknown`, and
`canGenerate=false` / `canSend=false`.

This establishes the NPC's pre-existing local presence, not evidence that
it is free, listening or unaffected by another scene. The strict
`readNpcSummonFacts` repository returns unknown for these values until
trusted structured evidence exists.

## Narrow first-contact design

For a **future new Discord message** addressed to an already-present NPC,
a trusted DM/operator can approve a bounded _scene policy_ for normal
conversation, rather than approving every utterance individually.
The proposed approval must be recorded and validated by a later
**world-scoped, authenticated and audited** repository:

- World, NPC, scene, original local-presence ID and NPC state version.
- Authorized issuer identity and actual world DM/operator role.
- Exact policy: allow direct speech, hold or deny.
- Trusted observed activity, awareness and other-scene occupancy.
- Issued and expiry timestamps, revocation status, reason/audit trail.
- Short duration (max 30 minutes for this isolated first-contact contract).
- Approval must **precede the original source event** and still be valid at
  processing time. A source event older than two minutes cannot be rehearsed.
- The actual original mapped player, bot-user mention, Discord route,
  immutable source event, NPC state and presence must be checked separately
  by the trusted DB/transport boundary and rechecked at action time.

A source event preceding approval cannot be retroactively authorized.
The consumed Sentinel inbound from M2.14 is **not** a live-response target:
a fresh event will be needed after future approved readiness evidence.

## Implemented in this slice

- `src/communication/scene-speech-readiness.ts`: strict, deterministic
  **advisory** check. It refuses summons, unverified direct contact, denied
  or revoked policies, spoofed claims, stale/mismatched evidence and source
  events predating approval.
- `src/offline/npc-speech-rehearsal.ts`: test-only composition with
  authoritative-snapshot and **fake-only** response ports, disabled outside
  `NODE_ENV=test` and when normal Discord, outbound or OpenAI provider is
  enabled. No retry on an uncertain fake result.
- Unit tests cover valid scope, future in-scene conversation, missing DM
  evidence, forged role assertions, grant/scene/version changes, NPC busy,
  unaware or in another scene, expiry, revocation and privacy-safe outcomes.

Every result preserves `canGenerate=false`, `canSend=false` and
`canGrantPresence=false`. An affirmative result is named
`fake_rehearsal_candidate`, **not** permission for a real model request
or live Discord send.

## What this does NOT prove

The test harness's `readTrustedSnapshot` and `runFake` collaborators
are injected mocks. This slice does **not** persist the approved policy,
authenticate a real Discord DM, query new trusted activity observations,
run an actual PostgreSQL-backed first-contact decision, or produce a
real or fake model-written NPC utterance in the owner DEV world.

That work still needs an independently reviewed implementation step
with provenance-bearing storage, trusted DM authorization, bounded
revocation, transaction locks and an actual disposable PostgreSQL
integration test. This will be coordinated with existing
[Issue #18](https://github.com/Strisko-SVK/living-world/issues/18).
The prior local-presence, immutable route and delivery fences from
M2.9/M2.10 remain mandatory.
