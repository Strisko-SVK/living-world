# M2.17 — Quartermaster in Discord DEV

The acceptance scene is a supply office aboard **Wayfarer Ledger** with two NPCs, Marcus Voss and Sentinel-001. The scene uses the existing Mac Gateway, PostgreSQL 17, Discord DEV guild and RAON tunnel to Hetzner. Live acceptance requires the owner's Mac, Discord account and human review.

## Start on the Mac

Run these commands from the existing Living World checkout in a shell with Node 22 and pnpm 10.17.1. If the branch already exists locally, use `git switch feat/m2-17-quartermaster`.

```sh
git fetch origin
git switch --track origin/feat/m2-17-quartermaster
pnpm install --frozen-lockfile
```

1. Keep the existing RAON listener on Hetzner at `127.0.0.1:8000` with a 4096-token context. If it is stopped, use the [existing startup commands](m2.16-raon-sentinel-discord-dev.md#1-use-the-existing-inference-process). Keep the existing tunnel open, or start it in a separate Mac terminal.

   ```sh
   ssh -i ~/.ssh/living_world_hetzner -o ExitOnForwardFailure=yes \
     -N -L 127.0.0.1:18000:127.0.0.1:8000 \
     "livingworld@${RAON_SSH_HOST:?set the existing VPS host}"
   ```

2. In the existing DEV Discord guild, select a new dedicated Public Thread in a parent text channel accessible only to test participants. Private Threads require explicit membership for the bot and each test player. Use a separate thread from the M2.16 scene. In the Discord Developer Portal, enable **Message Content Intent** for the existing bot. Grant **View Channel**, **Read Message History**, **Send Messages in Threads** and, for managed webhooks, **Manage Webhooks** on the approved parent. Give each test player access to view, read and post in the approved thread. The [Gateway docs](https://docs.discord.com/developers/events/gateway#message-content-intent) describe the intent, and the [webhook docs](https://docs.discord.com/developers/resources/webhook) describe parent-channel permission and the thread destination.
3. Keep the existing `.env.gateway-dev.local`, `.env.gateway-smoke.local` and `.env.gateway-player.local` with the local DEV database, bot credentials and `LW_PILOT_TEST_USER_ID`. Set the following values in the private `.env.raon-dev.local`. You can keep the manual webhook for M2.16 in its original config and leave `LW_RAON_NPC_WEBHOOK_URL` unset for this managed webhook trial.

   ```dotenv
   LW_RAON_SCENE=quartermaster
   LW_RAON_PARENT_ID=<DEV parent text channel ID>
   LW_RAON_THREAD_ID=<DEV thread ID>
   LW_RAON_INACTIVITY_MINUTES=10
   # Optional comma-separated Discord user IDs, up to three in addition to the owner.
   # Set the roster before the first prepare of this thread.
   # LW_RAON_ADDITIONAL_PLAYER_IDS=
   RAON_BASE_URL=http://127.0.0.1:18000
   RAON_CONTEXT_TOKENS=4096
   LLM_MODEL=Raon-1-nano
   LLM_TIMEOUT_MS=90000
   RAON_DEV_OUTPUT_TOKENS=192
   ```

   The timeout is a configurable DEV diagnostic setting. Measure actual latency. Stop the other Gateway session before starting this one.

4. Start and verify the existing PostgreSQL volume. Make the following local backup before applying additive migration `0020_raon_conversations`. If the DB was never provisioned, use the [Gateway DEV DB setup](gateway-dev-local-db.md).

   ```sh
   curl -fsS --max-time 10 http://127.0.0.1:18000/health
   docker compose --env-file .env.gateway-dev.local -f compose.gateway-dev.yml up -d --wait
   node --env-file=.env.gateway-dev.local --import tsx src/admin/gateway-dev-db.ts check
   (
     umask 077
     backup="living-world-dev-before-m217-$(date +%Y%m%d-%H%M%S).dump"
     docker compose --env-file .env.gateway-dev.local -f compose.gateway-dev.yml exec -T postgres \
       pg_dump -U postgres -Fc living_world_gateway_dev > "$backup" &&
     docker compose --env-file .env.gateway-dev.local -f compose.gateway-dev.yml exec -T postgres \
       pg_restore --list < "$backup" >/dev/null
   )
   node --env-file=.env.gateway-dev.local --import tsx src/admin/gateway-dev-db.ts migrate
   pnpm admin:raon --prepare
   pnpm admin:raon --check-raon
   LW_RAON_SESSION_APPROVED=true pnpm admin:raon --run
   ```

5. Wait for `raon_session / ready`. In the approved thread, select the real bot from Discord's mention picker and send `@Living World [Quartermaster] How are you today?` Then send `What happened?` and `Who requested it?` as ordinary messages. Use `[Sentinel] What is the alert level?` to switch, and `[Quartermaster] Back to those valve kits.` to return. You can also use Discord's **Reply** on a previously delivered NPC message addressed to you in this scene. Use `/end-npc` as ordinary message text to close focus. In a shared scene use a native reply or mention to address another player, or prefix out-of-character messages with `//`, `((`, or `OOC:`.
6. Press **Ctrl+C** once and wait for `raon_session / stopped`. Keep the tunnel up for a Gateway restart. Run the same `--run` command again. To test recovery, send a fresh follow-up within the configured inactivity interval. For the abrupt-exit scenario use an isolated DEV trial, terminate the dedicated process and then restart it. Allow policies created by this runner are recovered under the exclusive DB session lock.

The other launch mode remains available as `LW_RAON_SCENE=sentinel` with the original route. An existing manual parent webhook URL can still be used by supplying `LW_RAON_NPC_WEBHOOK_URL` locally. For managed reuse across threads, keep the same parent and change only the approved thread ID before preparing the second scene and restarting. Each launch supervises one approved route. Start a separate approved parent to test automatic provisioning. An existing roster cannot be silently changed through a rerun.

## Routing, memory and delivery

- Selection is deterministic. A verified bot mention with bracketed alias, a single configured NPC address, a native reply resolved from the recorded delivery ID, or one active focus identifies the target. Unknown bracketed aliases, ambiguous names, peer mentions/replies and OOC markers stop before inference. A plain message from a mapped player with active focus is treated as a follow-up. Free-form chat without an addressing cue is indistinguishable from NPC dialogue in that window. Use the addressing conventions above or close focus before unrelated discussion.
- Focus belongs to the world, scene and player and expires based on the source snowflake. A switch changes focus. Each NPC's recent dialogue and relevant older excerpts come from acknowledged outbox deliveries to the same player in the exact bound scene and mapping. Up to five recent turns and three bounded excerpts are sent, selected from at most 36 prior delivered turns. The provider counts the rendered context and uses a compact prompt under pressure. Player statements and earlier NPC dialogue are attributed conversation.
- The existing context builder retrieves scene state, known facts, attributed reports, observations, rumours and explicitly authored personal recollections. The public synthetic fixture source markers establish disclosure for these records. The existing general visibility rules apply to other worlds. Restricted knowledge and unclassified memories stay out of prompt context, and known restricted values are filtered from dialogue. The NPC can suggest a bargain. Dialogue writes interactions and delivery evidence. Inventory and authorization changes use their own mechanisms.
- An approved bot-owned webhook is discovered by its dedicated name, owner, guild and parent. Provisioning requires scoped permission and a verified source. The channel webhook is reused across personas and threads. The transport independently verifies the webhook and exact Discord source/destination. Timeout or lost acknowledgment after a send leaves the outbox uncertain. Use a fresh user message after reviewing the thread.
- Webhook delivery sets the stored NPC display name and avatar. The two DEV avatars are distinct Discord CDN placeholders. Native typing is emitted by the bot account. The Gateway keeps an in-memory queue of four events and performs bounded inference. Events over 120 seconds old and events predating the session are ignored. Restart preserves DB evidence and never replays Gateway events.
- Logs use trace IDs and fixed outcomes for routing, memory counts, model context and usage, inference timing, validation, policy renewal, typing, webhooks, delivery and end-to-end timing. RAON benchmark output includes its synthetic speech for human review. Protect logs alongside DEV credentials.
