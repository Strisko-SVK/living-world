# M2.18 — Discord-native NPC lifecycle

1. Start Gateway once on the Mac with `LW_DISCORD_NATIVE_DEV=true pnpm dev:npc`.
2. Open the approved Discord DEV server.
3. Create an ordinary text channel called **quartermaster-office**.
4. Initialize Quartermaster by selecting the real bot from the Discord mention picker and sending `@Living World [Quartermaster] {enable}`.
5. Create a thread called **Supply negotiation** from that channel using the Discord UI.
6. Start talking. Send `Hello, I need to talk about supplies.` as an ordinary message and continue with `What are we running low on?`.

Wait for `native_gateway / ready` before sending commands. The server owner uses **One-time setup** below for the first launch. Routine onboarding takes place in Discord. The alternate `/npc enable npc:Quartermaster` performs the same operation.

## One-time setup on the existing Mac

Use Node 22 and the repository's pinned pnpm. Keep the existing dedicated DEV PostgreSQL volume, bot token, allowed guild ID and RAON connection.

```sh
git fetch origin
git switch --track origin/feat/m2-18-discord-npc-lifecycle
pnpm install --frozen-lockfile
```

If the branch already exists locally, use `git switch feat/m2-18-discord-npc-lifecycle`. Stop the existing Sentinel or Quartermaster pilot before starting this Gateway. The two launch modes share an exclusive local DB lease.

1. Keep the RAON listener on Hetzner and the existing Mac tunnel open. Follow the [M2.16 server and tunnel commands](m2.16-raon-sentinel-discord-dev.md#1-use-the-existing-inference-process) if they are stopped. Verify `curl -fsS --max-time 10 http://127.0.0.1:18000/health`.
2. Keep `LW_DEV_GUILD_ID` and the dedicated DB values in `.env.gateway-dev.local`, plus `DISCORD_TOKEN` in `.env.gateway-smoke.local`. Keep `DISCORD_ENABLED=false`, `DISCORD_OUTBOUND_ENABLED=false` and `LLM_PROVIDER=disabled` as the base environment. The opted-in DEV launch selects RAON explicitly. Existing RAON settings in `.env.raon-dev.local` still apply. It requires a 4096-token context. The native entry point derives all route IDs from Discord and ignores `LW_RAON_PARENT_ID`, `LW_RAON_THREAD_ID`, `LW_RAON_SCENE`, player IDs and manual webhook URLs.
3. In the Developer Portal, enable **Message Content Intent** for the existing bot. The guild installation needs the `bot` and `applications.commands` scopes. In permitted roleplay channels grant **View Channel**, **Read Message History**, **Send Messages**, **Send Messages in Threads**, and **Manage Webhooks** to the bot. Players use Discord's corresponding view, read, post and create-thread permissions. For a Private Thread, add both the bot and participating players as thread members. The native Discord typing indicator uses the bot's identity. [Discord Gateway docs](https://docs.discord.com/developers/events/gateway#message-content-intent) · [Discord permissions](https://docs.discord.com/developers/topics/permissions) · [Discord webhooks](https://docs.discord.com/developers/resources/webhook).
4. Before starting, check the exact DEV DB, back it up and apply additive migration `0021_discord_npc_lifecycle`. The existing Mac data remains in the same volume.

   ```sh
   docker compose --env-file .env.gateway-dev.local -f compose.gateway-dev.yml up -d --wait
   node --env-file=.env.gateway-dev.local --import tsx src/admin/gateway-dev-db.ts check
   (
     umask 077
     backup="living-world-dev-before-m218-$(date +%Y%m%d-%H%M%S).dump"
     docker compose --env-file .env.gateway-dev.local -f compose.gateway-dev.yml exec -T postgres \
       pg_dump -U postgres -Fc living_world_gateway_dev > "$backup" &&
     docker compose --env-file .env.gateway-dev.local -f compose.gateway-dev.yml exec -T postgres \
       pg_restore --list < "$backup" >/dev/null
   )
   node --env-file=.env.gateway-dev.local --import tsx src/admin/gateway-dev-db.ts migrate
   LW_DISCORD_NATIVE_DEV=true pnpm dev:npc
   ```

5. As the **Discord guild owner**, run `/npc register` once in an accessible text channel, or mention the bot with `@Living World {register}`. To constrain the campaign to a single Discord RP category, run `/npc register-here` or `@Living World {register-here}` from a channel inside that category instead. This action instantiates both catalog NPCs once in one shared DEV campaign. It associates the guild owner with the Living World administrator role.
6. Grant campaign roles in Discord with `/npc access user:<member> role:Player` or `role:DM`. Campaign roles are additional to Discord permissions. The user picker operates on Discord accounts. The administrator can remove access with the same command. The guild owner can play and initialize bases immediately after registration.

The new DEV campaign initializes the existing Quartermaster and Sentinel templates once. The old one-scene worlds from M2.16 and M2.17 preserve their test data and can still be launched with their documented commands. Their transcripts stay scoped to those worlds and connections. Use a fresh ordinary channel for the native acceptance. An existing legacy-mapped channel requires a separate migration of that specific route.

## Discord commands

| Command                           | Who                 | What it does                                                                               |
| --------------------------------- | ------------------- | ------------------------------------------------------------------------------------------ |
| `/npc list`                       | Campaign members    | Shows NPC names and short aliases.                                                         |
| `/npc info npc:Quartermaster`     | Campaign members    | Shows availability and the base if the caller can access it.                               |
| `/npc bases`                      | Campaign members    | Lists accessible, enabled bases.                                                           |
| `/npc enable npc:Quartermaster`   | DM or administrator | Registers the current text channel and provisions the managed webhook.                     |
| `/npc status npc:Quartermaster`   | Campaign members    | Shows current base and availability.                                                       |
| `/npc disable npc:Quartermaster`  | DM or administrator | Disables the base from within its channel. History is retained.                            |
| `/npc reassign npc:Quartermaster` | DM or administrator | Changes the base to the current eligible text channel. Location and history are retained.  |
| `/npc scene npc:Quartermaster`    | DM or administrator | Registers the current channel as a shared scene at the selected NPC's known home location. |
| `/npc install`                    | Administrator       | Instantiates any newly released catalog templates once.                                    |
| `/npc access`                     | Administrator       | Grants, changes or removes campaign access.                                                |

Mention forms support `{enable}`, `{disable}`, `{status}`, `{reassign}`, `{info}` and `{scene}` after a bracketed NPC name. `{list}` and `{bases}` follow the bot mention alone. The commands resolve trusted aliases and execute application operations. The LLM receives NPC dialogue only.

## Architecture and boundaries

- Guild registration persists a campaign/world link, an owner and an optional approved category. Each role maps a Discord account to a player entity. The application uses current Discord account and channel access plus persistent campaign authorization.
- NPC registry records point to existing NPC entities and templates. Home location and Discord base are separate records. Registering, disabling or reassigning a base leaves NPC physical state alone. A shared channel is explicitly registered by a DM with a known narrative location. An approved channel cannot infer a physical location from an arbitrary NPC call. Existing remote or force-summon features stay on their separately authorized paths.
- Each normal thread derives its scene from the approved parent. The creation event and first eligible message share the same idempotent mapping. The actor and creator must have campaign access. Discord category, channel permissions, thread state and explicit private membership are checked. Archive and deletion close transport access. Channel renames preserve mappings.
- The default NPC applies in a dedicated base thread. Parent channels and shared scenes require explicit addressing or a reply to an acknowledged NPC message. In a base thread, ordinary text can start or continue an eligible conversation. Use Discord Reply/mention to address another player or an OOC prefix such as `//`. `/end-npc` as text closes focus. An explicit address restarts it or resumes after ten minutes of inactivity.
- The native branch validates source identity and fresh Discord text before lazy initialization. Membership and parent registration must already have been valid at the event timestamp. Scene mapping, presence and policy generated at receipt are checked against the exact bound interaction. M2.16/M2.17 retain their earlier pre-event policy and mapping checks. The outbox and conversation repositories continue to scope history by player, scene and NPC.
- One parent webhook is discovered by its app name, creator and parent destination. The registry stores its Discord ID. Tokens are rediscovered in memory. Delivery sends the configured NPC identity and revalidates the destination. An uncertain send is retained in the durable outbox and never retried automatically.
- The Gateway queues up to eight dialogue turns across its registered scenes, in receipt order, against the existing single RAON inference slot. Conversation state stays isolated between concurrent conversations. The Gateway uses the SDK's reconnect behaviour and rechecks permissions at delivery. The policy manager reuses or renews its exact bounded allow. Signed-in Gateway sessions share one DEV DB lock. A restarted session reuses eligible active policies or renews its near-expiry permits. Holds, denials and unrelated permits block only their scoped scene/NPC. Ordinary shutdown and restart require no SQL cleanup.
