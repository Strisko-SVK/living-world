# M2.15N — migration 0019 read-only preflight and DEV cutover gate

## Objective

M2.15M has been squash-merged into `main`. The new schema and guarded
one-shot functions exist **in repository code and disposable CI databases
only**. The owner's dedicated `living_world_gateway_dev` database is
**not** migrated by a Git merge.

This milestone introduces a **read-only** operator preflight for migration
`0019_dev_first_reply_consents` before the owner considers authorizing
a local DB change. It has no action that can migrate, write, create a
fixture, connect to Discord, or generate/send a response.

## Command — PREVIEW ONLY, not executed on owner's machine in this PR

Once separately approved for local read-only inspection:

```bash
node --env-file=.env.gateway-dev.local --import tsx src/admin/dev-first-reply-migration-preflight.ts --preview
```

No owner action is needed yet. The command accepts no other flags, and
`--apply`, `migrate`, `--force`, `--send` and `--reset` are rejected.

The existing dedicated local environment must pass all checks:
PostgreSQL URL `127.0.0.1:55432/living_world_gateway_dev`, role
`lw_gateway_dev`, matching local credentials, Postgres major version
**17**, non-superuser/non-CREATEDB/non-CREATEROLE and exact database
ownership. Discord, outbound and LLM must all be disabled. The CLI
does not log connection strings or private Discord content.

Its first SQL statement in the transaction is
`SET TRANSACTION READ ONLY`. It then applies an eight-second
statement timeout and reads only PostgreSQL catalog and Drizzle
migration metadata. No world/player/NPC message data is selected.

## Fail-closed result contract

Every output reports `readOnly=true`, `canMigrate=false` and
`canSend=false`. Outcomes:

| Outcome                                      | Meaning                                                                                                                                                          | Allowed next step                                                                                     |
| -------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| `ready_for_backup / pending_exactly_0019`    | Exactly 0018 is applied, required 0018 guards are intact, 0019 table/function/triggers do not exist                                                              | Review migration diff and obtain/verify a fresh DEV backup; seek **separate owner approval** to apply |
| `already_applied / already_applied_verified` | Exact 0019 migration history and intact guarded schema                                                                                                           | Stop migration process and proceed only with separately approved private DEV fixture planning         |
| `blocked / ...`                              | Unknown database/role, local migration drift, missing/drifted journal, broken 0018 baseline, partial 0019 installation, disabled/mismatched guards or read error | Stop; do **not** migrate or try to repair automatically                                               |

Migration history is pinned to all reviewed entries through 0019, their
timestamps and the reviewed SQL Git blobs. **No later/extra migration
is silently accepted.** On an already-applied database the preflight also
verifies the exact `guard_dev_first_reply_consent()` PostgreSQL
function body against reviewed SQL, both enabled trigger types,
all ten constraints including the original event/interaction unique
keys, the complete 20-column shape, the index and row-level-security
state. Partial installation and unknown drift are blocked.

A positive preflight is advisory **only**; it does not issue owner
approval, perform backup, or enable the existing
`gateway-dev-db.ts migrate` command.

## CI and security review

The isolated GitHub Actions PostgreSQL 17 service applies migration 0019
to a disposable database, then verifies the **already applied** verdict
against the actual system catalogs. Unit tests exercise pending,
already-applied, partial/malformed history, wrong target, unsafe
environment, forbidden flags, redacted errors and read-only-first
transaction ordering. PostgreSQL itself rejects a DDL statement inside
the read-only transaction.

No PR here modifies a migration, Drizzle journal, schema, runtime sender,
webhook, LLM, or deployment configuration. PR remains Draft pending
exact-head CI/security review and separate owner merge approval.

## Critical path to the FIRST real Sentinel reply

1. **Owner decision** for merging this read-only preflight (no DEV DB
   modification). Record exact merged `main` CI.
2. **Separate DEV migration decision**: later run the preflight,
   verify identity, validate a fresh recoverable backup and the exact
   migration diff; only then seek **explicit approval** to apply 0019.
   Do not apply until a specific owner go/no-go.
3. **Separate DEV scene provisioning decision**: create a fresh
   private parent/thread, isolated DEV world, mapped test player,
   Sentinel presence and host scene speech policy **before** the new
   message. The consumed prior Sentinel event must never be replayed.
4. **Real inbound and operator authorization**: with distinct approval,
   receive a new SDK-authenticated Discord event, inspect the original
   source and grant the event-specific one-shot **after** reception.
   `operator_entity_id`/DB role are attribution, not proof of an
   independently authenticated host/DM action.
5. **One real send boundary**: implement and review exact target
   allowlist, fresh DB/permission revalidation, durable attempt claim
   before HTTP, no retry after an uncertain ACK, sanitized audit and
   a hard stop. Only then request separate owner approval for one
   fixed harmless reply `Acknowledged. Standing by.` in the original
   private thread. The paid LLM remains disabled.

Owner verification is visual: precisely one correctly routed Sentinel
message, with no duplicate, cross-thread leak or unauthorized reply.
This is **not accomplished** by a green offline test.
