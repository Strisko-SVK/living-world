**State:** New implementation on a Draft PR, not yet approved for merge or owner-local apply. Base: M2.12 squash-merged `main` at `9f83273caeb2f0529dc295c0a0a16b3a4d66772e`; post-merge [CI #42048302048](https://github.com/Strisko-SVK/living-world/actions/runs/42048302048) PASS.

## Purpose and product scope

Create a **third, separately routed, synthetic test world** before beginning practical NPC E2E acceptance. Step 8's pristine `lw-dev-gateway-001` and Step 14's **consumed** `lw-dev-pilot-001` must remain unchanged. New key: `lw-dev-npc-e2e-001`. The new default-deny fixture reuses the validated `provisionDevFixture` logic to create a test world, a scene, a synthetic Sentinel NPC, a location, a player-character **without Discord identity mapping**, and a scene mapping with **no pinned NPC**. This means an NPC is **not** permanently assigned to a Discord thread.

This is **transport/test scaffolding only**, not the intended final product rule that players or DMs can summon NPCs in an ongoing scene. Future domain routing must respect DM authority, available NPCs, visibility and Discord permissions; it must not require individual NPC Discord membership per thread. All response generation and outbound delivery remain disabled.

## Scope and operational guardrails

- The CLI lives in `src/admin/discord-npc-e2e-fixture.ts`; there is **no import into normal runtime, Gateway, HTTP or delivery workers**.
- Its default command and `--preview` are nonmutating. `--apply` requires exact `lw-dev-npc-e2e-001` world and `living_world_gateway_dev` database confirmations. **Documenting this command does not authorize running it.**
- Validate the existing private DEV route and the prior pilot route from local env. A third, new parent+thread must not reuse any channel/thread IDs from either. Guild must remain the same DEV guild.
- The database URL must resolve to the dedicated local PostgreSQL 17 on `127.0.0.1:55432`, `living_world_gateway_dev`, using `lw_gateway_dev` non-superuser credentials. The CLI checks actual database name/role/version/superuser status inside the transaction. It rejects enabled inbound/outbound Discord, enabled LLM, production mode, remote DB endpoints and URL overrides.
- The shared fixture enforces a unique parent mapping, default-deny intake, no player identities, no local presence, no interactions, no deliveries, no policy audit and conservative replay/conflict checks.
- Unit tests validate ID collisions, wrong guild, unsafe environment, exact apply arguments, DB identity and failed preflight. Existing PostgreSQL tests validate the shared transactional `provisionDevFixture` code with synthetic random routes and cleanup.
- No DB migration, network login, Discord message, paid provider call, webhook, live operation or deployment is part of this PR. No real user IDs or secrets are committed.
