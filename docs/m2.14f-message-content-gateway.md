# M2.14F — Isolated DEV Message Content diagnostic/transport opt-in

**Status:** Draft PR only. No portal setting changes, live Gateway connection, Discord send, owner-local DB writes, deployment, or paid model calls.

## Evidence from third bounded Sentinel attempt

The owner reported these exact diagnostic stages (no token or message body):
```
target_thread_event_seen
normalization_content_unavailable
message_normalization_rejected
```
An independent owner-local read-only preview returned `status=ready_for_inbound`,
`playerMappings=1`, `activePresence=1`, `interactions=0`, `deliveries=0`.
The Gateway delivered a message event from the exact approved public thread,
past sender/type checks, but Discord's SDK did not supply usable text. No
persistence occurred. **The exact cause of withheld/empty content is still
unknown**; it is not appropriate to blame thread membership or to loosen
the intake trigger/authorization.

According to the [Discord Gateway documentation](https://docs.discord.com/developers/events/gateway#message-content-intent),
the `MESSAGE_CONTENT` privileged intent normally controls `message.content`,
but directly mentioning an app is supposed to be an exception. Since the
owner used a Discord mention picker, we must not assume the privileged intent
is required without further safe evidence. The diagnostic now explicitly
classifies whether the SDK's `mentions.users` metadata contains the bot's
identity, without printing that ID, private content, or other guild events.

## Owner-controlled privileged capability (optional, isolated DEV only)

**Security impact:** Requesting `GatewayIntentBits.MessageContent` broadens
what message text the connected bot *can* receive in all channels it already
has access to, not just the target thread. It **cannot** be restricted to
one thread at the Discord Gateway intent level. The in-process filter continues
to inspect and persist only events in the exact owner-approved guild/thread,
and no source content is logged. Keep the DEV bot access limited to the isolated
test scene. **Changing Developer Portal settings requires separate explicit
owner approval.** No application or other bot runtime is altered by this PR.

In the default runner, `Guilds` + `GuildMessages` remain unchanged.
The new privileged path requires **all three**:
1. A new, distinct owner authorization for the increased
   `MESSAGE_CONTENT` capability, and its enabling in the Discord Developer
   Portal (Bot > Privileged Gateway Intents > Message Content Intent). The
   Portal state cannot be verified by offline preflight. Discord may disconnect
   unauthorized privileged Gateway IDENTIFY with close code `4014`.
2. A one-time explicit environment acknowledgment
   `LW_NPC_E2E_PRIVILEGED_CONTENT_APPROVED=true` scoped to just that process.
   Never add a token or privileged bypass to a shared environment file.
3. All exact 17 existing live `--connect` confirmations **plus** the final
   `--confirm-message-content-intent` switch. A malformed/missing
   confirmation fails before any DB connection/Gateway call.

### Non-network read-only preflight — only after code merge

No privileged capability is requested in this step:
```bash
LW_NPC_E2E_PRIVILEGED_CONTENT_APPROVED=true node \
  --env-file=.env.gateway-dev.local \
  --env-file=.env.gateway-smoke.local \
  --env-file=.env.gateway-pilot.local \
  --env-file=.env.gateway-npc-e2e.local \
  --import tsx src/admin/discord-npc-e2e-inbound.ts \
  --preflight --check-message-content-intent
```

Expected event: `npc_e2e_message_content_preflight_valid`. It checks the
dedicated local PostgreSQL/world and the explicit process-only gate;
**it does not connect to Discord and cannot validate Portal permissions**.
If it fails, do not proceed. The regular `--preflight` stays unchanged.

### Future live one-shot (DO NOT RUN WITHOUT TWO SEPARATE APPROVALS)

The owner must separately approve the **privileged intent access** and the
**one new, bounded live Gateway test**. A code-only merge is NOT approval
for either. Under those explicit approvals and a green local preflight,
the isolated operator uses the same 17 exact confirmed flags for world,
context, guild, parent, thread, DB, `--inbound-only --one-message`, followed
by `--confirm-message-content-intent`; prefix the command with
`LW_NPC_E2E_PRIVILEGED_CONTENT_APPROVED=true`.
Only one new human-authored true bot mention sent after
`pilot_gateway_ready` qualifies. The runner never sends/replies/edits,
does not use an LLM, and stops after one accepted message or timeout.

If a failure occurs, capture only sanitized diagnostic stages. In particular:
`bot_mention_metadata_present`, `bot_mention_metadata_absent` or
`bot_mention_metadata_unavailable` accompany
`normalization_content_unavailable`. Do not send another message, retry,
or reactivate the fixture without inspecting read-only readiness and new
owner authorization.

This is an **opt-in isolated diagnostic transport**, not a permanent
decision to run production NPCs with privileged MessageContent. Revisit the
least-privilege alternatives once the original empty-content cause is known.
