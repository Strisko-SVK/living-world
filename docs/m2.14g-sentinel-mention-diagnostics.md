The Gateway received an event in the exact target thread; the sender, thread
and adapter normalization checks passed, **including nonempty content**.
The filter then rejected the target mention. No message was accepted or
persisted; the 90-second timeout followed. The exact reason for
`mention_rejected` is **not known from this log**.

The strict test requires **one actual Discord user mention of this specific
DEV bot**. Writing or pasting the visible string `@Living World`, tagging a
role, tagging a different user/bot, or including multiple recognized users
cannot satisfy this policy. Discord's mention editor can render a genuine
selected mention as a clickable/highlighted entity. Do not relax the filter
to accept plain display names, which can collide or be impersonated.

## Privacy-safe classification added to the shared pilot filter

An optional diagnostic observer receives exactly one additional, fixed reason
**only after verifying the authorized guild/thread and sender**. No raw
content, user/channel/message snowflake, token or payload is logged:

| Diagnostic reason | Interpretation |
|---|---|
| `mention_target_not_literal` | Message content does not contain a literal user mention of this DEV bot and SDK does not report it; may be plain typed text |
| `mention_target_only_in_metadata` | Discord SDK reports the bot mentioned, but it is not literally present in the message text; metadata alone does not count |
| `mention_other_user_only` | One or more actual user mentions exist, but none targets this bot |
| `mention_target_missing_from_metadata` | The literal `<@bot>` form is present but Discord SDK does not confirm the bot mention |
| `mention_multiple_user_targets` | Bot is mentioned but one or more *other* users are recognized as well; strict one-target pilot rejects |
| `mention_inconsistent` | Fallback if message text/SDK normalizer representation violates the expected invariant |

The existing `mention_rejected` stage remains as a stable final umbrella
classification for historical tests/diagnostics. Default and privileged
Gateway configurations, text and alias matching, route, mapped human identity,
one-shot latch, DB assertions and no-send/no-LLM controls do **not** change.

All cases are exercised entirely offline with synthetic discord.js events.
The test suite asserts fixed reason codes, strict rejection and that no
user IDs, bot IDs, secret tokens or message bodies are emitted in diagnostics.
