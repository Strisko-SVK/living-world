# M2.15J — first NPC reply preflight, fake-only

## Goal

Prepare the next narrow gate toward one **owner-visible Sentinel reply in a
private DEV scene** without silently granting model or Discord permissions.

M2.15I already proved that one original, SDK-shaped _synthetic_ inbound
interaction can reach PostgreSQL response/outbox and a fake ACK. M2.15J
checks the exact proposed first-reply target **before** any response starts.
The first pilot reply is predetermined: `Acknowledged. Standing by.`
It requires no live LLM generation.

## Read-only, scoped assessment

`createOfflineFirstReplyPreflight` returns a sanitized, fixed-vocabulary
`npc_first_reply_preflight` verdict. It accepts only a strict proposed
world/NPC/scene/interaction, player entity, original Discord message and exact
guild/parent/thread. It reads the original source and M2.15I's _trusted
PostgreSQL_ `received`-phase snapshot via an injected read port. The port
must not accept caller-supplied permissions, DM identity or timestamps.

A `fake_only_candidate` requires all of the following:

- Execution is in the isolated test process with Discord, outbound and real
  LLM explicitly disabled.
- The immutable original source matches the exact world, player, NPC,
  interaction, Discord message ID, guild, parent and thread.
- The interaction is a fresh `received` Discord interaction with no local
  preparation, generated content, claim or delivery outbox record.
- The authoritative scene contact and active host operator policy pass the
  existing `assessOfflineSpeechReadiness` check: same world/scene/NPC,
  pre-event presence, current NPC revision, a non-revoked and non-expired
  time-limited approval, `free` activity, `aware` perception and no competing
  scene. The underlying snapshot verifies mapped player, unique alias and
  original unchanged route.
- No other information, proposed DM role, `execute` flag or extra attribute
  may extend the strict input schema.

**Every verdict**, including a positive fake-only candidate, has
`readOnly=true`, `wouldSend=false`, `canGenerate=false` and
`canSend=false`. There is no network client, provider, webhook, operator
secret or database writer in the implementation. No test creates a durable
owner-consent grant.

## Automated acceptance evidence

- Unit tests cover positive fixed-text preview, mismatched world/NPC/scene,
  player, source event, exact route, forged `ownerApproved`/`dm`/`execute`
  flags, malformed evidence, absent/reused outbox, missing/revoked/expired
  host approval, busy NPC, competing scene and safe error diagnostics.
- The existing disposable PostgreSQL 17 Sentinel integration test calls the
  preflight using **the same original SDK-shaped fake-client inbound**
  persisted by the existing Discord intake. The underlying trusted snapshot
  is read from actual transaction state, not asserted by the caller.
- The expected output is fake-only and no-send. A wrong thread is denied.
  After the existing fake response/outbox ACK, the same preflight is denied.
  Every test mutation is inside rollback-only CI transactions.

## Still required before the first live DEV send

1. Separately approved private DEV fixture/new thread and a **fresh actual
   authenticated Gateway event after host speech approval**, never a replay
   or reset of the consumed Sentinel source event.
2. A real authenticated host/operator consent mechanism with an explicit
   one-shot, time-bounded, auditable allowlist. This module's preview
   **is not that consent** and is not sufficient to authorize sending.
3. Real action-time database revalidation at generation/transport and the
   HTTP network boundary, including permissions/route/host approval,
   one first attempt and no automatic retry on uncertain ACK.
4. A separately owner-approved one-message, harmless, fixed-text Discord
   send with correct private thread destination, rate limits, audit and stop.
   Real model generation and broader NPC behavior require a later approval.

This PR must stay **Draft** pending independent code/security review,
all CI checks and separate owner merge approval. It performs no deployment,
no changes to the owner's `living_world_gateway_dev`, no Discord Gateway
login/send, no webhook and no paid LLM call. No schema migration.
